## Item 2 — `neon_x4 -> neon_x1` tail chain

- Obstacle found and recorded (relayed from R2 as well): the amd64 wrapper contract
  `KSpec`/`wrapper_correct` in `Hashtree/Proofs/WrapperAmd64.lean` contains
  `fin.tail = none`. That is **false for shipping multi-lane kernels**: neon_x4 ends with
  `.bTail "hashtree_sha256_neon_x1"`, i.e. `halted := true, tail := some …`. Any ARM wrapper
  proof built on that contract would be vacuous. The ARM wrapper must model the tail chain
  explicitly: callee region / stack shift (x4 restores `sp` by `addi 31 31 1024` before the
  tail branch), the shared return marker (`x30`, untouched by both kernels), and then the
  x1 leg *from the tail-entry state*.
- Second, independent obstacle: `neon_x1_correct` is stated only for the fresh
  `entryS 0` shape. The x4 tail state has rodata pointers in x3–x18 that `entryS` models as
  numeric junk, so the x1 leg cannot be re-used by substitution: it needs either a
  generalized x1 contract over an arbitrary initial register file, or a second x1 tree
  generated from the fixed exit cut `T0b.KF` (the cut is fixed; only the `σ` substitution
  varies). The second is the cheap, sound route and is the plan.
- Plan: `KSpecArm` = {halted, err = none, tail = some callee, sp restored, scratch
  footprint, tail-state = `mapState env σ T0b.KF`}; compose with a `KSpecArm` for x1 whose
  entry premise is the x4 exit cut. Reuse R2's chain-aware module if it lands on
  `origin/research/formal-r2-amd64`; otherwise keep the ARM chain local (different ISA types,
  so no direct reuse anyway).
- **Built (2026-11-13):** the chain split is proved at the model level, premises-first —
  `ArmCall.neon_x4_chain_of_cut` (x4 tail cut) and `ArmCall.wrapper_neon_of_cut` (composed
  with the #79 wrapper).  The remaining premises are exactly the two per-kernel products:
  (a) the x4 stream's `run` from `neonEntry` reaching the tail cut, and (b) the x1 leg's
  `runChain` from that cut (the second x1 tree from the fixed cut).  See "Chain contracts"
  below.  For reference, the regenerated `ArmShaX1L` tree (the sha_x1 kernel) builds:
  `It0` 97 slices / 167 steps, `T0a`/`T0b` 1 slice / 5 steps, 0 output bytes without a
  proof — so the sha_x1 counts stay proved; the `neon_x1` leg from the cut is still the
  blocked per-kernel product, not a chain obligation.

  core) changed.  Contents:
  - `renameInstr f` renames only `.bTail`; `renameState f` maps only the pending `tail`
    name.  Neither `outBytes` nor `abiObs` reads `tail`, so observations are untouched.
  - `exec_rename`: `exec` commutes with `renameInstr`/`renameState` for all 42 `Instr`
    constructors (the work is `Except` bind/map distribution, the two-state `foldl`/`foldlM`

    unchanged "pc out of program" failure string.
  - `run_renameProg`, `renameProg`, `renameProgs`: per-program/per-list rename of both the
    lookup name and the instruction stream.
  - `runChain_rename`: the call chain commutes, starting from a renamed state and returning the
    renamed final state with `f` applied to every path name.  Premises:
    (i) `hfind` — whenever the linux list finds `n` with `p`, the renamed list finds `f n` with

    produce, so nothing is lost.

    `halted = true`, `tail = none`, the same `outBytes`, and the same `abiObs` as the linux

  (a few seconds).
- Tree generation: `./.lake/build/bin/armloop1 <kernel> <headPc> <blocks> <dir> [maxLen]`
  (`sha_x1 8 1 … 160`; `neon_x1 9 1 … 160`; `neon_x4 13 4 … 160`).
- **Memory rule on this VM:** never run a slicer uncapped. Use
  `systemd-run --scope --quiet -p MemoryMax=60G -p MemorySwapMax=0 <cmd>` (or
  `ulimit -v 62914560`), one process at a time, and timebox a strategy to 10 min.
- Kill policy: `kill <PID>` only, PID from `ps`/`pgrep`.
- Rename module: `lake build Hashtree.Asm.ArmRename` (in `formal/lean`), 6 jobs, **2.6 s** per
  build, run under `systemd-run --scope -p MemoryMax=60G -p MemorySwapMax=0`; no proof search,
  no heavy run.  The proof is pure rewriting/simp over the existing `Arm`/`ArmRun` models; the
  only iteration cost was the module build, so the 10-minute strategy box was never relevant.
- Rename proof recipe (reusable): state every commutation inward, `renameState f (s.op ...) =
  (renameState f s).op ...`, as `@[simp]`; never put `renameState` itself in a simp set (it is a
  `def`, unfolding it breaks the `@[simp]` matching); pure helpers get `getC (renameState f s) =
  getC s` rfl lemmas.  The loads/stores are carried by `Except`/`okOr` algebra
  (`except_bind_pure`, `except_bind_map`, `except_map_bind`, `okOr_map_rename`, `except_map_ite`,
  `okOr_ite`) plus two-state `foldl`/`foldlM` commutations; `by_cases s.halted = true` before
  `cases i`; `split <;> simp_all` is the fallback for the branching/`ret` cases.  In the chain
  proof the load-bearing trick is normalising the `renameState` projections before rewriting,
  and using the `err = none` premise (`fail_err`) to exclude the unknown-program branch.
- Chain-contract recipe (reusable): the one-hop split is a single
  `simp only [runChain, hfind, hrun, htail, herr]` — `runChain`'s equation lemma unfolds the
  `hops+1` branch, the `find?`/`run`/`tail`/`err` premises reduce the two matches, and the
  `let (r, path) := …; (r, name :: path)` result is definitionally the pair of projections, so
  no `cases` or `split` is needed.  The specialized contract is then
  `rw [runChain_tail …, hx1]`; the composed wrapper theorem is an `exact wrapper_neon …` with
  the derived `hsc` and the exit-cut structure's fields as the remaining premises.
- Chain module build: `lake build Hashtree.Asm.ArmCall` (in `formal/lean`), 6 jobs, seconds,
  under the same `systemd-run --scope -p MemoryMax=60G` cap; no proof search.  The wrapper
  module's 31 warnings are all pre-existing (`if_true`/`if_false` deprecations and unused
  section variables); the chain-contract declarations add none.

  CBNZ -> shani`; NEON: `addi sp,sp,2048; BL x4; subi sp,sp,2048; ret`; shani:
  `BL sha_x1; ret`.
- Stack arithmetic to prove: entry SP = S (16-aligned); NEON callee entry SP = S+2048, x4
  allocates 1024 (SP = S+1024 in the body) and restores to S+2048 before the tail, x1
  allocates 64 and returns, wrapper `subi` returns SP to S. sha path: callee entry SP = S,

  wrapper at the recorded pc, then run the wrapper epilogue. Plan: a small
  `Hashtree/Asm/ArmCall.lean` `runCall` (depth-1 call stack) plus a `KSpecArm` that carries
  the callee entry SP and the return pc, with **no** `fin.tail = none` premise. Not built.

### Chain contracts: x4 tail cut and x1 exit cut (2026-11-13)

The `hsc` premise of `wrapper_neon` is now discharged structurally by a proved chain split,
so what is left in it is only the two per-kernel products, in exactly the cut shapes the
generators produce.

`runChain_tail` (generic glue): if `progs.find? (·.name = name) = some p` and
`run p.code p.ro m0 … fuel s = scut` with `scut.tail = some t`, `scut.err = none`, then
`runChain … (hops+1) name s = ((runChain … hops t {scut with pc := 0, halted := false,
tail := none}).1, name :: (…).2)` — one hop, the tail-entry state, the name prepended to the
path.  `runChain_single` is the one-hop return case (`sc.tail = none` gives `(sc, [name])`),
used for a leg that ends in its own `ret`.

`NeonX4Cut sp0 scut` (the x4 tail contract's cut predicate):
`scut.halted = true`, `scut.tail = some "hashtree_sha256_neon_x1"`, `scut.err = none`,
`scut.getG 30 = <rRet,2>` (the shared return marker: the x4 stream must not clobber `x30`, so
the x1 leg entered from the cut returns to the wrapper's return pc), and
`scut.getG 31 = <rStack, sp0+2048>` — the last is the stack-shift/frame obligation: the
`addi 31 31 1024` pair at the x4 exit balances the 1024-byte x4 frame, so the `neon_x1` leg
is entered with the same `SP` the wrapper handed `neon_x4` (the wrapper's moved `SP`).

`neon_x4_chain_of_cut`: premises `hf : progs.find? (·.name = "hashtree_sha256_neon_x4") =
some x4`, `hrun : run x4.code x4.ro m0 … fuel (neonEntry count sp0) = scut`,
`hcut : NeonX4Cut sp0 scut`, and `hx1 : runChain … hops "hashtree_sha256_neon_x1"
{scut with pc := 0, halted := false, tail := none} = (sc, path)`.  Conclusion:
`runChain … (hops+1) "hashtree_sha256_neon_x4" (neonEntry count sp0) = (sc, "hashtree_sha256_

### x30-offset relabeling: proved (2026-11-13)

`Hashtree/Asm/ArmRet.lean` (new module, no `sorry`) supplies the run-level relabeling the
`ArmShaX1L` tree cannot state itself.  For a stream that never touches `x30` (`NoTouch`, a
decidable predicate scanned by `decide`), replacing the offset of `x30`'s `<rRet, ·>` pointer
(`retOff k`, region kept) commutes with `exec` and with `run`:

  `exec_retOff : NoTouch i → s.getG 30 = .ptr ⟨rRet, o⟩ →
       exec … i (retOff k s) = retOff k (exec … i s) ∧ (exec … i s).getG 30 = s.getG 30`
  `run_retOff  : prog.all (fun i => decide (NoTouch i)) = true →
       run … n (retOff k s) = retOff k (run … n s)`

Recipe.  The second conjunct is a per-instruction `x30`-preservation theorem (`exec_getG30`),
proved with an `Ok30` algebra over the `Except` bodies: for every body form there is a lemma
that the resulting state keeps `getG 30` of the input state (`ok30_setG/setW/setQ/setD/
setFlags/halt/branch/writeBack/storeLane/storeVal/storeLanes/loadReg/storeReg/ld1Step/
ld4Step` and the `foldlM`/`foldl` lifts).  The commutation pushes `retOff` through the same
bodies with the corresponding `retOff_*` lemmas instantiated against the `NoTouch` components
(`retOff_getG k s i h`, `getC/getW/getX_retOff`, `addrWB_retOff`, `writeBack_retOff_out`,
`loadReg/storeReg_retOff`, `foldlM_ld1/ld4_retOff`, `foldl_st1/st4_retOff`, `okOr_retOff`,
`except_map_ite/bind`, and the pure builders).  `run_retOff` is the fuel induction, using
`exec_getG30` to carry the invariant `s.getG 30 = <rRet, o>` to the next iteration.

Cost.  Module 1140 lines (`38` constructors × 2 conjuncts); `lake env lean
Hashtree/Asm/ArmRet.lean` 1.8 s; `lake build Hashtree.Asm.ArmRet` well under 2 min (7 jobs);
peak memory far under the 60 G cap.  51 linter warnings (redundant `simp only` args), no
errors, no `sorry`.

Consequence for the tree gap.  The `x30 = <rRet, 0>` constant of the generated `entryS 0` is
no longer an obstacle: any run proved from return pc 0 transfers to the wrapper's call site
(return pc 1) provided the stream passes the `NoTouch` scan (the three ARM kernel streams do
by `decide`).  What still blocks the `ArmShaX1L` instantiation is (ii) the stack shift for an
arbitrary `sp0` — the tree's stack accesses are the absolute `[-32, 0]` range around `SP = 0`
— and (iii) the final-state extraction: the tree proves the exact `= mapState EF σ KF`
equality that the driver's `sha_x1_correct` currently discards.

### Stack-shift simulation for `sp0`: generic part proved (2026-11-13)

`Hashtree/Asm/ArmShift.lean` (new module, no `sorry`) and `Hashtree/Asm/ArmShiftCall.lean`
(new module, no `sorry`) supply the `rStack`-offset simulation, and
`Hashtree/Proofs/ArmShaX1Exit.lean` instantiates it at the `sha_x1` entry and exit cuts:

  `entryS_map_sh : mapState env σ (entryS k) = sh k (mapState env σ (entryS 0))`
  `retOff_sh     : retOff kk (sh k s) = sh k (retOff kk s)`
  `run_rel       : prog.all Canon = true → ro ≠ rStack → k % 16 = 0 →
       Rel k s1 s2 → Rel k (run prog ro (memSh k mem0) orc n s1) (run prog ro mem0 orc n s2)`
  `sha_x1_run_shift_sp : sp0 % 16 = 0 →
       Rel sp0 (run prog 4 (memSh sp0 mem0c) orc fuel (retOff 1 (entryS sp0 at σ)))
                (run prog 4 mem0c orc fuel (retOff 1 (entryS 0 at σ)))`
  `sha_x1_run_exit_sp  : … → ShaX1Exit sp0 (run prog 4 (memSh sp0 mem0c) orc fuel …)`

Relation design.  `Rel k s1 s2` keeps gpr/vr/mem/pc/halted/tail/err/assume equal after shifting
the `rStack` region of `s2`, so the memory field is the shifted write log (`shLog k`).  Flags
cannot be shift-invariant: `cmp` of two stack pointers compares offsets, and the shifted side
sees both offsets `+ k`.  `FlRel k` therefore accepts either the exact pair or the pair shifted
on both components; `none`/`some` mixes are impossible.  This is enough because `cmpr` on success
overwrites flags and on failure preserves the input flags (handled by `FlRel_fail_any`).

Whitelist.  `Canon` accepts exactly the instruction shapes of the shipped streams (subi, adrp,
addLo12, addr, vop, rev32, the sha256 ops, b, ret, cmpr, bcc, ld1, st1, ldp/stp .d);
`FlagFree = Canon` minus `cmpr`/`bcc`, which are proved separately (`exec_cmpr_rel`,
`exec_bcc_rel`).  `canon_of_get` turns the run's `prog[pc]? = some i` into `Canon i = true`.
`bcc` needs `decideC` never to be `none` for `Int` (`decideC_some`, `decideC_shift`), so
`assume` does not grow differently on the two sides.

Instantiation recipe.  `sha_x1_run_shift_sp` chains `entryS_map_sh`, `retOff_sh`, `rel_sh` and
`run_rel` with `hcanon : ShaX1.prog.all Canon = true` (`rw [← Array.all_toList]; decide`) and
`hro : (4 : Region) ≠ rStack`.  `sha_x1_run_exit_sp` rewrites the base run by
`sha_x1_run_relabeled` and applies `ShaX1Exit_shift` to `sha_x1_exit`; `ShaX1Exit` needs no
flag equality, so the shifted final flags are harmless.  Note the shifted run starts from
`memSh sp0 mem0c`, not `mem0c` — the shift is also applied to the initial stack memory.

Cost.  `ArmShift.lean` 1206 lines, `ArmShiftCall.lean` 58 lines; `lake env lean` 1.0 s and
1.4 s respectively (under `systemd-run --scope -p MemoryMax=60G -p MemorySwapMax=0`), builds
7 and 21 jobs; only unused-simp-argument warnings, no errors, no `sorry`.  `sha_x1_run_shift_sp`
and `sha_x1_run_exit_sp` elaborate with the existing 415-job `ArmShaX1Exit` build.

Remaining boundary (the deferred memory step).  What is still not proved is that
`memSh sp0 mem0c` agrees with the driver's initial memory `mem0c` on the footprint the kernel
reads/writes (plus the entry-state identity with `ArmCall.shaEntry`).  Until that footprint
lemma lands, `sha_x1_run_exit_sp` is a stack-shift statement at a *shifted* initial memory, and
`proofs.json` stays at the conservative status (gate theorem `out_final`, fixed c=2).

### Memory question at the `sha_x1` legs: shift the base side instead (2026-11-13)

#### Renumbering seams at the wrapper entry (review follow-up)

The leg contracts start at `pc = 0` in the leg's own numbering, while the shared `ADD $2048`
runs before the branch in the real #82 code.  The seam is now explicit, not a silent pc
identification:

* `renum s = { s with pc := 0, halted := false, tail := none }` resets a wrapper state to the
  leg-stream convention.
* `renum_addi_shaWrap82 : renum (Arm.exec rNum m0 (fun _ => false) (.addi 31 31 2048)
  (entry count sp0)) = shaWrap82 count sp0` - the shared `ADD` from the wrapper entry lands at
  `(shaWrap82 count sp0).next` (`pc = 1` in the pre-branch numbering); the renumbering gives the
  leg entry `shaWrap82 count sp0` (`pc = 0`) whose stream is `shaniPath82`.  The two pcs are
  distinct: the ADD ran at `pc = 0`, the leg stream is indexed from 0 only after the reset.
* `sha_x1_wrapper_82_entry` - the entry-level corollary: the #82 `sha_x1` path assembled from
  `entry count sp0`, with the shared `ADD` executed and renumbered by the lemma above before
  `runCall` consumes `shaniPath82`.
* `neonPath_82_shape` - the NEON side of the same pin: the modeled #82 NEON path is the
  renumbered `[ADD; BL neon_x4; SUB; RET]`.  The branch's unconditional `JMP done` is absorbed
  (both arms reach the same shared `done:`), and the call marker `2` is the index of the shared
  `SUB $2048` (the real `done:`) in that renumbered stream.  This is a renumbering claim, not a
  literal instruction-sequence equality: the real stream contains `CBNZ`/`JMP`, and the model's
  per-path stream does not.  The only `pc` reset on the NEON path is the callee-entry one that
  `wrapper_neon` already performs explicitly (`{ C with pc := 0, halted := false, tail := none }
  = neonEntry`, by `rfl`), so `wrapper_neon` / `wrapper_neon_of_cut` apply to #82 unchanged.
