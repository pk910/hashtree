## Item 1 — every count, including c = 0

### sha_x1: proved for every count (this milestone)

- Driver `Hashtree/Proofs/ShaX1All.lean` (namespace `Hashtree.Proofs.ArmSha`):
  `sha_x1_correct (c : Nat)` states, from `mapState env0 σ (entryS 0)`,
  `fin.halted = true ∧ fin.err = none ∧ fin.tail = none ∧ InRange … ∧ OutOk …` for the
  full `steps c` run, with `steps c = NP + (if c = 0 then T0a.NS else It0.NS + (c-1)*It.NS + T0b.NS)`;
  `sha_x1_hyps_sat` discharges the rodata/`HMem` well-formedness hypothesis.
- Generated tree: `Hashtree/Gen/ArmShaX1L/{Head,It0,It,T0a,T0b}` (regenerated with
  `./.lake/build/bin/armloop1 sha_x1 8 1 Hashtree/Gen/ArmShaX1L 160`).
- `lake build Hashtree.Proofs.ShaX1All` completed successfully (olean in
  `.lake/build/lib/lean`, 2026-11-12 23:28Z). Every slice is `decide +kernel` on
  `sliceCheck` plus per-lane `bv_decide`, so this is kernel-checked, no `sorry`.
- The tree is *not* committed (Gen is regenerated + packed); the deterministic generator
  + driver are.

### neon_x1: driver ready, tree generation **blocked** (not proved)

- Driver `formal/lean/NeonX1All.lean` (kept at the lean root until its tree exists, so
  that `make build` does not pick up a module whose generated imports are missing):
  same structure as `ShaX1All`, conclusion `neon_x1_correct (c : Nat)` from
  `mapState env0 σ (entryS 0)` with `steps c` as above, plus `neon_x1_hyps_sat`.
- The loop generator now supports the multi-lane head (`Cfg.countHead`: the head compares
  the count register `x2` with 4, `cmpi 2 4` at pc 13 / `cmpr 0 2` at pc 9) and emits
  `KF_tail` from the final cut (`some "hashtree_sha256_neon_x1"` for x4, `none` for x1).
- **Blocker: the adaptive slicer's symbolic states blow up once the spill area is modelled
  correctly.** Two measured runs (`armloop1 neon_x1 9 1 <dir> 160`, one process at a time):

  | bound | slices | wall | peak RSS | result |
  |---|---|---|---|---|
  | `lo = -32` (wrong) | 28 | 15 s | ~2 GB | completes, but the body stores at `[sp,#-64]`, outside the modelled frame: `It0/Final.log_final` is false, so the tree is unsound |
  | `lo = -64` (correct) | 34 (It0), 34 (It) | 7.5 min → killed | 159 GB | It0 completed (39 files); It reached slice 31/34 of `genSeg`, no file written for 5+ min |

  The correct bound is required: the prologue allocates 64 bytes and the body's spill at
  `[sp,#0]` is address `sp0-64`, so `lo` must be `-64` (the first version took the min over
  the *prologue log* only, `min 0 spLo` with `spLo` the final `sp`, which gives the needed
  `-64`; the old `-32` was a real generator bug, not a modelling choice).
- Mitigations tried: `Sl` now stores the cut *trees* instead of the whole symbolic run state
  (peak at slice 31 of It0 fell from 67 GB to 42 GB) — a real improvement, not enough.
  Per-slice cost grows sharply near the end of a segment (`99 %` CPU, no progress), so this
  is expression growth in the cut/derivation, not a leak in `out`.
- **Not proved.** Do not claim neon_x1 counts; `proofs.json` still says `c = 2` and `c = 0`
  (`ArmNeonX1P`/`ArmNeonX1P0`), which is what stands today.

## Item 2 — `neon_x4 -> neon_x1` tail chain

- Obstacle found and recorded (relayed from R2 as well): the amd64 wrapper contract
  `KSpec`/`wrapper_correct` in `Hashtree/Proofs/WrapperAmd64.lean` contains
  `fin.tail = none`. That is **false for shipping multi-lane kernels**: neon_x4 ends with
  `.bTail "hashtree_sha256_neon_x1"`, i.e. `halted := true, tail := some …`. Any ARM wrapper
  proof built on that contract would be vacuous. The ARM wrapper must model the tail chain
  explicitly: callee region / stack shift (x4 restores `sp` by `addi 31 31 1024` before the
  tail branch), the shared return marker (`x30`, untouched by both kernels), and then the
  x1 leg *from the tail-entry state*.
- Second, independent obstacle: `neon_x1_correct` is stated only for the fresh
  `entryS 0` shape. The x4 tail state has rodata pointers in x3–x18 that `entryS` models as
  numeric junk, so the x1 leg cannot be re-used by substitution: it needs either a
  generalized x1 contract over an arbitrary initial register file, or a second x1 tree
  generated from the fixed exit cut `T0b.KF` (the cut is fixed; only the `σ` substitution
  varies). The second is the cheap, sound route and is the plan.
- Plan: `KSpecArm` = {halted, err = none, tail = some callee, sp restored, scratch
  footprint, tail-state = `mapState env σ T0b.KF`}; compose with a `KSpecArm` for x1 whose
  entry premise is the x4 exit cut. Reuse R2's chain-aware module if it lands on
  `origin/research/formal-r2-amd64`; otherwise keep the ARM chain local (different ISA types,
  so no direct reuse anyway).

## Item 3 — PR #79 arm64 wrapper

- `wrapper_arm64.s` is post-#79 (commit 42836eb, "arm64: keep the NEON kernel frame inside
  the Go frame (#79)"): frame `$2048-24`; R0/R1/R2 = output/input/count; `MOVBU hasShani;
  CBNZ → shani`; NEON path `ADD $2048, RSP; BL hashtree_sha256_neon_x4; SUB $2048, RSP; RET`;
  shani path `BL hashtree_sha256_sha_x1; RET`.
- Shipped `.syso`: `hashtree_linux_arm64.syso` is an `ar` archive of the kernel objects
  (`sha256_armv8_neon_x1.o`, `..._neon_x4.o`, `..._crypto.o`); it contains **no**
  `HashtreeHash` symbol, so #79 (a change to the Go assembly) needs no `.syso` rebuild. The
  archive does export `hashtree_sha256_neon_x4`, `hashtree_sha256_neon_x1`,
  `hashtree_sha256_sha_x1`, so the tail-calling chain is the shipped one. The syso was last
  regenerated in #74; that is not a gap for #79.
- Proof status: **not started** (needs items 1–2). The wrapper statement to prove:
  16-byte alignment preserved (`$2048` is a multiple of 16), `ADD/SUB $2048` cancel, the
  k2/k3 (x19/…, new Go ABI) registers preserved, and the NEON path is unconditional from
  the wrapper's point of view.

## Recipes / cost

- Generator build: `cd formal/lean && export PATH=/root/.elan/bin:$PATH && lake build armloop1`
  (a few seconds).
- Tree generation: `./.lake/build/bin/armloop1 <kernel> <headPc> <blocks> <dir> [maxLen]`
  (`sha_x1 8 1 … 160`; `neon_x1 9 1 … 160`; `neon_x4 13 4 … 160`).
- **Memory rule on this VM:** never run a slicer uncapped. Use
  `systemd-run --scope --quiet -p MemoryMax=60G -p MemorySwapMax=0 <cmd>` (or
  `ulimit -v 62914560`), one process at a time, and timebox a strategy to 10 min.
- Kill policy: `kill <PID>` only, PID from `ps`/`pgrep`.
