# R5 — windows/amd64 proofs (VM1)

Branch: `research/formal-r5-windows`, from `origin/research/formal-r2-amd64` at `fca5ff4`.
Machine: `root@46.101.165.150` (24 vCPU), clone `/root/hashtree-win` (throwaway, `.lake` local).

## Result in one paragraph

The simplest of the six COFF kernels, `avx512_x16`, now has a **functional contract on the
shipped windows stream**: `Proofs/WinAvx512.win_out` states, for every input block and every
output byte, that the byte written by the windows kernel is the SHA-256 byte of its block --- the
same Go-facing statement as the linux `Gen.Avx512X16P.Final.out_final`, on the windows
instructions.  It is derived from the linux certificate by a machine-checked register-renaming
simulation (`win_transfer`, built on the `Win64` engine), and the per-instruction identity of the
two *generated* streams is checked in-module as well (`win_correspondence`, a kernel-checked
comparison of all 3247 instructions); the only remaining input is the identity of
the two models with the `.syso`/`.o` artifacts, which `formal/ci` re-derives on every CI run.
The other five kernels differ from linux by a **stack frame** (push/sub prologue, save block,
restore block, add/pop epilogue, tail calls, early-return entry points).  For the three frame
kernels that return directly, `Proofs/WinShani`, `Proofs/WinSseX1` and `Proofs/WinAvxX1`
establish the whole Win64 ABI/frame model on the shipped streams: body correspondence (668, 4180
and 4049 instructions), stack footprint including the shadow space, callee-saved GPR coverage,
push/pop pairing, `rsp` balance, the `xmm` save area and callee-saved vector coverage; section 11
does the same for the two chain kernels `avx_x4` and `avx2_x8` (all six streams now have a static
ABI/frame model on the shipped bytes).
The frame equivariance itself is now proved for `shani_x2`: `Proofs/WinFrameStack` is the
composed per-instruction engine (`exec_comb = exec_shiftPc . exec_ren . exec_frame`, the last one
transporting the state through the `rsp` move `spSt d` with the displacement shift `addDisp d`
under `δ + d = 0`), and `Proofs/WinShaniTransfer.shani_body_transfer` instantiates it on the
shipped streams: `n` steps of the windows body from the translated body-entry state are exactly
the translation of the `n` linux body steps, for any run that stays in the body slice, with a
kernel-checked scan (`body_safe`, no `native_decide`) of all 668 body instructions.  What remains
for a full `shani_x2` contract is the prologue/epilogue *replay* (11 + 12 concrete `exec` steps)
and the final composition with the linux certificate; the mechanism for the composition is the
existing frame rule `X86Frame.run_fr` (section 6).
`U6` is formalized for `avx512_x16`: the kernel never mentions `rsp`, therefore it cannot save or
restore `xmm6`-`xmm15`, and a concrete prefix witness shows `xmm6` destroyed.  The wrapper is
staged on R2's chain-aware tail-call contract (`Proofs/X86Chain`, imported verbatim) instantiated
for the four windows streams in `Proofs/WinChain`; the per-link `KSpecC` obligations and a Lean
model of the Go wrapper text are the two remaining inputs (section 7).

## 1. The Win64 state model

`Hashtree/Proofs/Win64.lean` (committed as `6b88c21`) is the reusable vocabulary:

| concept | definition |
|---|---|
| callee-saved GPRs | `winCalleeGpr = [rbx, rbp, rdi, rsi, r12, r13, r14, r15]` = `[3,5,7,6,12,13,14,15]` |
| callee-saved vector registers | `winCalleeVec = xmm6..xmm15` = `[6..15]` |
| shadow space | `shadowLo = 8`, `shadowHi = 40`, i.e. `[entry_rsp+8, entry_rsp+40)` |
| frame | `WinFrame sp D a := a.region = rStack ∧ sp - D < a.off ∧ a.off < sp + 40` |
| callee-saved obligation | `WinCalleeSaved s0 s` (entry values preserved) |
| return-target shape | `IsRet v := ∃ o, v = .ptr ⟨rRet, o⟩` |

The model of the machine is unchanged: `gpr : List (Val W32 Int)` (16 entries), `vr : List (List
W32)` (32 registers x 16 lanes), a write log `mem`, `flags` as the last control comparison, `pc`,
`halted`, `tail`.  `rsp` is register 4 and holds a pointer, `.ptr ⟨rStack, off⟩`; `push`/`pop` and
`sub/add rsp, imm` are the only writers.

The ABI engine is the *register renaming*: `RenPerm F G` (a permutation of `0..15` with
`F rsp = rsp`), `renSt F G s` (register `F j` of the image holds register `j` of `s`),
`rlI F` (relabel the GPR operands of an instruction), `okI` (operand registers < 16), and

* `exec_ren` — execution is equivariant under a `RenPerm` (all 39 instruction forms);
* `run_ren_upto` — `run winProg ... n (renSt F G s) = renSt F G (run linuxProg ... n s)` given
  the instruction-by-instruction program identity and `okI` on every fetched instruction;
* `run_gpr_len`, `run_nofail`, `run_pc_upto` — bookkeeping for the induction (the register file
  keeps its length, the run does not fail, the pc stays in range).

## 2. What the six streams actually are (from the models)

All six bodies are the linux body **renamed**; none has a different body.  What differs is the
ABI prologue/epilogue and the pc numbering.  Measured from `Hashtree/Kernels/X86Win/*.lean`
(`F` below is the linux->windows GPR map; `dpc` the instruction shift; `disp` the stack-
displacement shift of `rsp`-based operands):

| kernel | prologue | epilogue | frame | pc shift | disp shift | F (linux -> windows) |
|---|---|---|---|---|---|---|
| avx512_x16 | none | none | 0 | 0 | -- | 1->9, 2->8, 6->2, 7->1, 8->10, 9->6, 10->7 |
| shani_x2 | `sub rsp,248`; 10 xmm saves [0,144] | 10 xmm restores; `add rsp,248`; `ret` | 248 | +10 (body 1..668 -> 11..678) | +160 | 1->9, 2->8, 6->2, 7->1 |
| sse_x1 | 9 pushes (rbx,r8,rsi,rdi,rbp,r12..r15); `sub rsp,192`; 8 xmm saves at [64,192) | `add rsp,192`; 9 pops; `ret` | 72+192=264 | +11 (body 7.. -> 18..) | 0 | 1->7, 2->8, 6->2, 7->1, 8->6 |
| avx_x1 | 9 pushes; `sub rsp,192`; 8 xmm saves at [64,192) | `add rsp,192`; 9 pops; `ret` | 72+192=264 | +11 (body 8.. -> 19..) | 0 | 1->6, 2->8, 5->7, 6->2, 7->1, 8->5 |
| avx2_x8 | `ret` at pc 3 (small-count entry path); 2 pushes (rbp,rsi); `mov rbp,rsp`; `and rsp,-32`; `sub rsp,1248`; r12..r15 QWORD saves + 10 ymm saves | `pop rsi`; `pop rbp`; `jmpTail avx_x4` | 16+1248=1264 | piecewise +11/+12 (body 14..3716 -> 25..3727, 3716..6072 -> 3728..6084) | 0 | 1->6, 2->8, 6->2, 7->1, 8->7 |
| avx_x4 | `ret` at pc 3; `sub rsp,568`; 10 xmm saves at [384,528] | `add rsp,568`; `jmpTail avx_x1` | 568 | piecewise +10/+9 (body 7..694 -> 17..704, 696..4141 -> 705..4150) | 0 | 1->0, 2->8, 6->2, 7->1 |

The two `avx_x4`/`avx2_x8` pc shifts are **not constant**, which is why section 11 proves their
body correspondence as two zipped scans with an explicit pc map rather than a `shiftPc p`.  For
both kernels the `.rodata` offsets (`MemRef.ro`) of the two streams are identical instruction by
instruction; the register substitution above is recovered from the streams and verified at every
body instruction (it is a substitution, not a permutation: both streams use different scratch
allocations).

Two structural facts that matter for the wrapper proof: `avx_x4` **tail-calls** `avx_x1`, and
`avx2_x8` tail-calls `avx_x4` (so `avx2_x8` -> `avx_x4` -> `avx_x1` is a chain whose frames must
compose), and four kernels have an early `ret` entry path for small counts.

The `avx512_x16` stream is the only one with no frame at all, which is why it was proved first.

## 3. The `avx512_x16` contract (`Hashtree/Proofs/WinAvx512.lean`)

Register permutation `F`/`G` above, `RenPerm` instance `renPerm` (all `decide`-checked), and
`okI` on every linux instruction (`linuxProg_ok`, 3247 instructions, `decide +kernel`).

* `windows_prog_correspondence` --- `∀ j < linuxProg.size, winProg[j]? = (linuxProg[j]?).map (rlI F)`.
  `linuxProg.size = 3247`; the windows stream has 3292 instructions, and the 45 extra instructions
  lie past the linux body, outside the transferred run.  Proved in-module as `win_correspondence`
  from `corrAll_eq : corrAll = true`, a kernel-checked comparison over the two shipped arrays
  (`decide +kernel`, no `native_decide` axiom; the 3247 instructions are compared as three zipped
  slices, see section 8).  The contract therefore has no external input left except the identity
  of the two *models* with the COFF/ELF objects, which `python3 formal/ci/proofs.py check`
  re-derives from the artifacts on every CI run (`model OK`).
* `win_transfer` --- the generic simulation: a linux run of `n` steps on `linuxProg` from `s`
  equals, under `renSt F G`, the windows run of `n` steps from `renSt F G s`.
* `win_run` --- `run winProg 4 mem0c orcC STEPS (renSt F G (mapState env0 σ (entryS 24)))
  = renSt F G (mapState (E217 env0) σ K217)`, where `STEPS` is the exact step count of
  `Gen.Avx512X16P.Final.run_final` (3248 instructions, from the certificate).
* `win_out` --- for every block `n < 16`, word `i < 8` and byte `b < 4`, the windows run's write
  log at `⟨rOut, σ 1 + 32n + 4i + b⟩` holds a cell whose byte `b` is
  `((node (blk inp n)).getD (4i+b) 0).zeroExtend 32` --- the SHA-256 byte of the block.
  Statement and proof mirror `Gen.Avx512X16P.Final.out_final` exactly; the windows-side
  ingredients are `win_run` and `renSt_mem`.
* Axiom status: `propext`, `Classical.choice`, `Quot.sound` and the `bv_decide` axioms of the
  imported certificate; **no `native_decide` axiom, no `sorryAx`**.  The correspondence check
  `corrAll_eq` is a kernel reduction (`decide +kernel`); the full R5 axiom list is recorded in
  `formal/notes/R5-audit.txt` and checked by `proofs.py check-audit` (section 8).

Timing (VM1): the module compiles in **4.1 s** (`lake build Hashtree.Proofs.WinAvx512`, after the
`Gen.Avx512X16P` chain is built).  The chain itself had to be built from scratch in this clone:
219 modules, **26m39s** (the run ended in the module's first elaboration, so the chain was
complete at that point).  `lake exe x86check` is the expensive check, not this module.

## 4. U6: the `avx512_x16` kernel clobbers `xmm6`-`xmm15`

Observation U6 in the roadmap.  Two machine-checked halves in `WinAvx512`:

* `win_no_rsp` --- the shipped windows stream **never mentions `rsp`**: a scan of all 3292
  instructions with `mentionsRsp` (a syntactic predicate over the 39 forms: `rsp` as a base or
  index register of a memory operand, as a source/destination GPR, or the implicit `rsp` write of
  `push`/`pop`) returns `true`, and `win_no_stack_access` gives it per instruction.  A kernel
  with no `rsp` mention cannot reserve a frame and cannot spill/restore a callee-saved vector
  register.
* `u6_witness` --- a concrete entry state (`r8 = 16`, `xmm6` = sixteen ones, everything else
  zero) where after only 15 instructions `getV 6` differs from the entry value.  The kernel
  destroys `xmm6` and never restores it.

Consequence for the caller-facing contract: **no windows contract for this kernel may assume
`xmm6`-`xmm15` survive the call**; the Go-facing `win_out` contract does not, and the wrapper
must save them itself if it needs them.  (Contrast: `shani_x2` saves and restores
`xmm6`-`xmm15`; `sse_x1` and `avx_x1` save and restore `xmm6`-`xmm13` and their shipped streams
never write `xmm14`/`xmm15` (`sse_no_xmm14_15`, `avx_no_xmm14_15`), so the callee-saved vector
set is covered there too; `avx_x4` and `avx2_x8` save vector state before their tail calls.  See
the table above.)

## 5. The ABI and frame models: `shani_x2`, `sse_x1`, `avx_x1`

One file per kernel: `Hashtree/Proofs/WinShani.lean`, `Hashtree/Proofs/WinSseX1.lean`,
`Hashtree/Proofs/WinAvxX1.lean`.  The theorem names quoted first are the `shani_` ones; the other
two files state the same facts with the `sse_`/`avx_` prefix on their own streams.  Everything is
checked against the shipped arrays (no external input).

### `shani_x2` (`WinShani`, 54 s, 36 s of it the 668-instruction `bodyOk_full` kernel
evaluation)

* `shani_body_correspondence` --- for all `j < 668`,
  `winProg[11+j]? = (linuxProg[1+j]?).map (bodyI F 160 10)`, i.e. the windows body instruction is
  the linux one with its `rsp`-relative displacements shifted by 160 bytes, its GPRs renamed by
  `F`, and its branch targets shifted by 10.  (`bodyI`, `addDisp`, `shiftTgt`; the comparison is
  `bodyOk`, a 668-element kernel evaluation.)
* `shani_stack_footprint` --- every memory operand of the kernel that addresses the stack has
  `0 ≤ disp` and `disp + width ≤ 248` relative to the running `rsp`.  With
  `shani_rsp_balanced` (`sub rsp,248` at pc 0, `add rsp,248` at pc 689, and no other write of
  `rsp`) the whole footprint is `[entry_rsp-248, entry_rsp)`; the return address
  `[entry_rsp, entry_rsp+8)` and the **shadow space** `[entry_rsp+8, entry_rsp+40)` are never
  touched.
* `shani_callee_gpr_untouched` --- no instruction writes `rbx`, `rbp`, `rdi`, `rsi`, `r12`-`r15`.
* `shani_prologue_saves` / `shani_epilogue_restores` / `shani_save_slots_untouched` --- the ten
  `xmm6`-`xmm15` saves (pcs 1..10, `[rsp+16k]`) are read back by the ten restores (pcs 679..688,
  same slots) and nothing in the body accesses the 160-byte save area.

Not proved, and clearly separated: the *semantic* lifting of these syntactic facts into an
invariant of the run (`WinCalleeSaved`).  That is the same missing lemma as section 6: it needs
`exec`-equivariance for "instructions that do not touch `rsp`/the frame".

### `sse_x1` and `avx_x1` (`WinSseX1`, `WinAvxX1`)

Both are the linux stream under the same kind of rewriting as shani but with **displacement shift
0**: the shipping code uses the same low offsets `[rsp, rsp+64)` in the linux `sub rsp,88` frame
and in the windows `sub rsp,192` frame; only the frame is larger, the extra 128 bytes at
`[rsp+64, rsp+192)` holding `xmm6`-`xmm13`.  Register maps: sse `1->7, 2->8, 6->2, 7->1, 8->6`;
avx `1->6, 2->8, 5->7, 6->2, 7->1, 8->5` (`rsp`, `rbx`, `rbp`, `r9`-`r15` fixed).  pc shift +11.

* `sse_body_correspondence` --- for all `j < 4180`, `winProg[18+j]? = (linuxProg[7+j]?).map
  (bodyI F 11)`; avx: 4049 instructions, windows pcs 19..4067 against linux pcs 8..4056.  The
  comparison is kernel-checked (`decide +kernel`, no `native_decide` axiom), as a scan over the
  zipped body slices (`bodyOk_full`), so the kernel reduction never indexes into the 4243-element
  array literal; the pointwise theorem is the `of_zip_scan` instance for the shipped streams.
* `sse_stack_footprint` --- every `rsp`-based operand of the whole 4243-instruction stream lies in
  `[rsp, rsp+192)` (chunked `decide +kernel` over 2048-element slices); with
  `sse_rsp_balanced` (`sub rsp,192` at pc 9, `add
  rsp,192` at pc 4206, no other `rsp` writer but the nine pushes/pops --- stated as the three
  segment scans `0..8`, `10..4205`, `4207..4242`) the footprint is
  `[entry_rsp-264, entry_rsp-72)`, i.e. below the pushed words and the return address, and the
  shadow space `[entry_rsp+8, entry_rsp+40)` is never touched.  `sse_body_footprint` --- the body
  itself only uses `[rsp, rsp+64)`.
* `sse_prologue_pushes` / `sse_epilogue_pops` / `sse_callee_saved_covered` --- 9 pushes
  (`rbx, r8, rsi, rdi, rbp, r12-r15`) and the 9 pops in exactly the reverse order; the pushed set
  covers `winCalleeGpr`.
* `sse_prologue_saves` / `sse_epilogue_restores` / `sse_save_slots_untouched` --- 8 saves at
  `[rsp+64, rsp+192)` (pcs 10..17, `xmm6`-`xmm13`), 8 restores at pcs 4198..4205, and no body
  access to the save area.
* `sse_callee_vec_split` / `sse_no_xmm14_15` --- `winCalleeVec = [xmm6..xmm13] ++ [xmm14, xmm15]`
  and the shipped stream never writes `xmm14`/`xmm15`; with the save/restore pair this covers
  the whole callee-saved vector set.

The `avx_x1` file has the same theorem set on its stream (4049-instruction body, prologue pcs
1..18, epilogue pcs 4068..4086, 4116 instructions in all); its restore block uses `vmovdqa`
(`vload true`) where the sse one uses `movdqa` (`vload false`), which is the only difference in
the statements.  Build times: `WinSseX1` 6.3 s, `WinAvxX1` 6.2 s.

Still not proved (same gap as shani below): the semantic lifting into a run invariant
(`WinCalleeSaved`) and the functional contract, section 6.

## 6. The frame kernels: the transfer, and what is left

### `shani_x2`: done at the body level (`Proofs/WinFrameStack`, `Proofs/WinShaniTransfer`)

For `shani_x2` the frames sit at the **same addresses**: windows `sub rsp,248` plus ten
`xmm6`-`xmm15` saves at `[rsp, rsp+160)`, linux `sub rsp,88`; the body was re-based by ten
instructions and every `rsp`-relative displacement grew by `160`, so with `δ = -160` (the state
relation `spSt δ`: windows `rsp` is the linux `rsp` lowered by 160) and `d = +160` (the operand
rewrite `addDisp d`) we have `δ + d = 0` and every effective address coincides
(`WinFrameStack.effAddr_mv`, proved from `plusI_plusI_add`).  The engine is the composition

```
bodyI F d p i        = shiftTgt p (rlI F (addDisp d i))          -- the generated shape
exec_comb            : exec (bodyI F d p i) (shiftPc p (renSt F G (spSt δ s)))
                         = shiftPc p (renSt F G (spSt δ (exec i s)))
                       = exec_shiftPc (exec_ren (exec_frame ...))
run_comb             : the same for `n` steps, by a single induction over `n`
```

with the syntactic side condition `frameSafe` (39 branches: `push`/`pop`/`ret`/tail calls are
excluded, `rsp` is never a value operand, an `rsp`-based operand has no index, no relocation and
`index ≠ rsp`, `gsSafe`/`vsSafe`), `frameSafe_trOk`, and the fact that `frameSafe` is exactly what
`exec_frame` needs (the body never writes `rsp`, so `spSt δ` commutes with every register write).
`Proofs/WinShaniTransfer` instantiates it:

| theorem | statement |
|---|---|
| `body_safe` | `((linuxProg.toList.drop 1).take 668).all safeB = true` (kernel scan, `decide +kernel`) |
| `body_hmap` | `winProg[10 + j]? = (linuxProg[j]?).map (bodyI F 160 10)`, `1 ≤ j < 669` |
| `body_hside` | per-pc `okI ∧ frameSafe` of the linux body |
| `shani_body_transfer` | `n` windows body steps from `shiftPc 10 (renSt F G (spSt (-160) s))` are `shiftPc 10 (renSt F G (spSt (-160) (n linux body steps)))`, as long as the linux run stays in the body slice |

Axioms of `shani_body_transfer`: `propext`, `Classical.choice`, `Quot.sound` (no `sorryAx`, no
`Lean.ofReduceBool`); `body_safe` uses only `propext`.  `WinSafeScan` builds the Bool mirrors the
scan needs: `decide (frameSafe i)` does **not** reduce in the kernel (the `mSafe` branch, and
`decidable_of_decidable_of_iff` is itself a `▸`-transport), so `frameSafeB`/`gsSafeB`/`vsSafeB`
are Bool-valued copies of the 39 branches, with `frameSafeB_iff` bridging them, and
`safeB = decide okI && frameSafeB`.

### The remaining composition (`shani_x2`)

The pieces fit together as follows (this is the plan of record; the prologue/epilogue replay is
the only part not yet machine-checked):

1. **Prologue replay** (11 `exec` steps, not yet done): from a Win64 call state `x`
   (`x.getG 4 = .ptr a`, 16 GPRs, not halted) the windows stream reaches pc 11 with
   `rsp = .ptr (a - 248)`, `vr` unchanged, and a write log `saveLog ++ x.mem` (`saveLog` = the
   160 cells of the ten `vstore` saves at `[a-248+16k]`, values `x.getV (6+k)`); the linux
   stream reaches pc 1 with `rsp = .ptr (a - 88)` and `x.mem`.
   *Subtlety found while assembling this:* the two `sub rsp, imm` instructions also set `flags`
   (`some (a.off, ofInt 248)` vs `some (a.off, ofInt 88)`), so the body-entry states differ in
   `flags`, and the reclaimed log of `exec`'s `sub` case shows the body's first instructions
   (`vload`, `lea`) do not clear flags.  Before `shani_body_transfer` can be applied, the
   composition needs a flags-insensitivity lemma for the body (the body does branch: a `jcc`
   occurs, but every `jcc` is preceded by a `cmp`/`test` in the generated code), or the initial
   flags have to be carried explicitly through both sides.
2. **Body**: `shani_body_transfer` with `s` = the linux body-entry state of step 1, `n = steps c`
   for the count the linux certificate uses, `lo = 1`, `hi = 669`, `hcond` from the linux
   certificate's slice invariant.
3. **Epilogue replay** (12 `exec` steps: ten `vload` restores, `add rsp,248`, `ret`), reading the
   save cells out of the log (`lookup` finds them because they are the newest writes of those
   addresses) and restoring `xmm6`-`xmm15` and `rsp`.
4. **Linux certificate**: the windows run then carries exactly the linux final state with
   `rsp`/`xmm` restored and the byte images renamed, and the extra `saveLog` cells.  The frame
   rule `X86Frame.run_fr` (`run prog ro mem0 orc n (fr M s) = fr M (run prog ro (view M mem0) orc
   n s)`, where `fr M s = { s with mem := s.mem ++ M }`) is what makes the extra saves harmless:
   the linux kernel is then run with the initial memory `view saveLog mem0`, i.e. the caller's
   memory seen through the save block -- and since the save block lies in
   `[a-248, a-88)`, disjoint from the linux 88-byte frame `[a-88, a)`, the `WfMem`/`EnvMem`
   hypotheses of the linux certificate transfer to `view saveLog mem0` by `view_other`.  The
   windows postcondition is the linux one with `InRange` widened from 88 to 248 bytes (the save
   block is inside the windows frame, below the return address; `shani_stack_footprint` gives
   `[rsp, rsp+248)`).
   Because writes prepend to the log, the `fr`/`view` trick applies when the kernel's entry log is
   empty (true for a call from the wrapper) and the seeded linux state is written as
   `fr saveLog P_l`, whose log is `[] ++ saveLog` -- the same log the windows prologue produced.

### `sse_x1`/`avx_x1`: a stack-memory shift, not a displacement rewrite

Those two streams keep the linux displacements (disp shift 0) and their frames differ by exactly
the 128 bytes of the `xmm` save area (`72+192` vs `48+88`), so in the body the windows `rsp` is
`entry_rsp-264` where the linux one is `entry_rsp-136`: every body stack access targets a cell
128 bytes *lower* in the `rStack` region than the corresponding linux access.  The frame lemma for
these kernels therefore cannot use the `addDisp Δ` rewrite of the shani case; the state relation
has to shift the stack part of the memory log by 128 (`⟨rStack, o⟩ ↦ ⟨rStack, o-128⟩`) and use
`sse_body_footprint`/`sse_save_slots_untouched` to show the shift is injective on the cells the
body and the save area touch.  The prologue/epilogue replays are 18 concrete `exec` steps in
(9 pushes, `sub rsp,192`, 8 saves) and 19 out (8 restores, `add rsp,192`, 9 pops, `ret`).

## 7. The windows wrapper (`$1024-24`)

`wrapper_windows_amd64.s` is **Go assembly**, not a COFF object: it is not in
`hashtree_windows_amd64.syso` and `formal/proofs.json` `wrapper_windows_amd64` has no `model`
(so the model/certificate gate does not cover it).  It now has a hand-written Lean model,
`Kernels/X86Win/WrapperWindows.lean`, and section 17 proves the wrapper's composition with a
kernel contract against it.  Its text:

```
TEXT ·HashtreeHash(SB), 0, $1024-24
  MOVQ output+0(FP), CX ; MOVQ input+8(FP), DX
  MOVQ R8, R12 ; MOVQ count+16(FP), R8     ; R12 is callee-saved in Win64: one save, in registers
  MOVQ SP, BX ; ADDQ $2048, SP ; ANDQ $~31, SP
  CMPB ·hasShani(SB), $0 ... CALL shani/avx512/avx2 dispatch
  MOVQ BX, SP ; MOVQ R12, R8 ; RET
```

so the wrapper (i) subtracts its declared frame `$1024` in the assembler prologue, then **adds
2048**, so `rsp` ends **1016 bytes above the entry `rsp`** and the `ANDQ $-32` alignment happens
there --- in the caller's frame, not below a reserved area; the text's `ADDQ $2048` does not track
the declared frame.  (With `$2048`, the open fix branch `fix/windows-wrapper-frame`, the add
cancels the subtraction and the aligned `rsp` sits just below the entry `rsp`, as on linux;
section 17 proves both placements.)  The wrapper (ii) keeps the old `rsp` in `rbx`
(callee-saved) and restores it exactly, (iii) preserves the Go `R8` argument across the call by
moving it to `r12`, and (iv) dispatches on three CPU-feature bytes.

Machine-checked, the consequence is stronger than a footprint mismatch (`WinShippedClobber`,
section 17): on the `avx2_x8` path the loop body is sequential from the guard at windows pc 24
to the loop-back at pc 6085, so a call with count ≥ 8 executes the input-derived 32-byte store
`vmovdqa [rsp+0x100], ymm8` at pc 442; with the shipped frame the body `rsp` is `σ9-264` or
`σ9-280`, so the store interval contains `[σ9-8, σ9+8)` --- it overwrites the Go caller's saved
`rbp` and return address with data loaded from the input block.  The same geometry is reached
through the `avx512_x16 -> avx2_x8` tail link, where `avx2_x8` is entered with `rsp = σ10` (the
tail `JMP` does not push a return address), so the same store covers the same two words.  Hence
PR #80's `$2048` is a memory-corruption / control-flow fix, not a footprint cleanup.

### The composition is chain-aware: R2's `X86Chain` (commit `6d27a36`)

Every multi-lane kernel **leaves through a tail call**, in the COFF streams exactly as on linux;
the windows models show it directly:

| kernel | small-count exit | tail |
|---|---|---|
| avx512_x16 | `.ret` at pc 3 | `.jccTail .b "hashtree_sha256_avx2_x8"` at pc 8 |
| avx2_x8 | `.ret` at pc 3 | `.jmpTail "hashtree_sha256_avx_x4"` at pc 6103 |
| avx_x4 | `.ret` at pc 3 | `.jmpTail "hashtree_sha256_avx_x1"` at pc 4162 |
| avx_x1, sse_x1, shani_x2 | -- | none (`ret` only) |

so `avx512_x16 -> avx2_x8 -> avx_x4 -> avx_x1` is one chain and only `avx_x1` returns for
arbitrary counts.  The linux `KSpec`/`callK` contract requires `fin.tail = none` and would
therefore be unsound for these kernels (see `formal/notes/R2.md`, "KSpec blocker": a `callK`
that discards a tail would run the wrapper's post code with the tailed kernel never executed).
R2 has since landed the chain-aware contract as `Hashtree.Proofs.X86Chain`
(`origin/research/formal-r2-amd64` at `6d27a36`): `Link`, `Spec`, `step`, `resume`, `chainRun`
(following `tail = some name` into the next link on the shared memory/return marker),
`callChain` (first link at pc 0, caller resumed with `pc/halted/tail` cleared), the per-link
obligation `KSpecC`, `chain_sound`, and `chainRun_fr` (framing across a whole chain).  That file
is imported **verbatim** into this branch (same blob as R2's) and instantiated for the windows
streams in `Hashtree/Proofs/WinChain.lean`; no parallel chain layer is introduced.

### The windows chain instantiation (`Hashtree/Proofs/WinChain.lean`)

* `winSpecs` --- the four shipped COFF programs in tail order, each with its tail-call name and a
  caller-supplied step function `steps : Nat -> Nat`; all four links currently use rodata region
  4 (`rRo`).  Per-link rodata regions need R2's region-renaming lemma (`WfMemAt` plus a rho
  simulation over `run`, which the coordinator reports is being added); the COFF kernels have the
  same multi-region tail structure as the linux ones.
* `win_chain_names` (`rfl`) --- the link list is exactly
  `["hashtree_sha256_avx512_x16", "hashtree_sha256_avx2_x8", "hashtree_sha256_avx_x4",
  "hashtree_sha256_avx_x1"]`, the names `chainRun` matches tails against.
* `win_chain_tails` (kernel `decide` over the shipped arrays) --- the tail instructions at the
  three concrete windows pcs (8, 6103, 4162) name the next link.
* `win_small_exit` (kernel `decide`) --- the small-count entry path at pc 3 of each multi-lane
  stream returns, so a link may also return before the chain is exhausted (`ChainPost`).
* `win_chainRun_returns` --- `chain_sound` specialised to the windows chain.
* `win_callChain_returns` --- the wrapper's call returns with `err = none`, `tail = none`,
  `halted = false`, `pc = 0` and the chain post-condition, given `KSpecC` and that the post is
  stable under `resume` (output/memory contracts are; the early-return disjunct of `ChainPost` is
  covered by `resume` leaving the memory and registers alone).
* `win_callChain_fr` --- the chain call commutes with a memory-log frame (`chainRun_fr`): the
  wrapper's earlier writes are the chain's initial memory and are appended to its log, so the
  call composes with the wrapper's own prologue writes.

Two inputs are still missing for a closed wrapper theorem, now with exact shapes: (a) `KSpecC`
for the four links --- `avx512_x16` on the full-body path at count 16 is
`Proofs/WinAvx512.win_out`, the three frame kernels have ABI/frame models only (sections 5-6),
and the small-count/tail branches need the pre/post bridge at the wrapper's call state
(`entryW`-style: `rcx`/`rdx`/`r8`, `rsp` 32-byte aligned, shadow space reserved); (b) a Lean
model of the Go wrapper text itself --- its `MOVQ`/`ADDQ`/`ANDQ`/`CMPB`/`CALL` sequence is Go
assembly, our `Instr` has no `call`, and the call is `callChain`; the rest is register
bookkeeping (`rsp` saved in `rbx` and restored exactly, `r8` saved in `r12` across the call).
With (a) and (b) the composition is `win_callChain_returns` applied to `winSpecs`, with
`win_callChain_fr` carrying the wrapper's write log.

Consequences for this workstream: the kernel-level windows theorems are unaffected, but
`win_out` (section 3) covers only the **full-body path**, count 16 (`hσ : σ 2 = 16`); for
smaller counts the shipped kernel tail-calls, and that path is stated through `callChain`, not
per kernel with a discarded tail.  `formal/proofs.json` keeps `wrapper_windows_amd64` at
`unproved` with the note pointing here.

## 12. The `sse_x1`/`avx_x1` stack-memory-shift engine

Section 6 left this as the outstanding engine.  The design is now pinned down far enough to
state exactly what has to be proved and why each side condition is needed.

**Why the shani engine cannot be reused.**  `exec_frame` needs `δ + d = 0`: the windows stream
must have its `rsp`-relative displacements shifted by the same amount its `rsp` is lowered, so
that both runs touch the *same absolute cells*.  `sse_x1`/`avx_x1` keep the linux displacements
(`bodyI F 11` is `rlI F` only), and their body-entry `rsp` is 128 lower (`entry_rsp-264` against
`entry_rsp-136`), so the windows body touches cells 128 below the linux ones.  A displacement
rewrite is impossible; the state relation must move the memory.

**The relation.**  Define one shift on addresses, on cells and on the state:

* `shAddr μ a` --- `⟨rStack, o⟩ ↦ ⟨rStack, o + μ⟩` (`μ = -128`), every other address fixed;
* `shCell μ` --- shifts the *payload* of `.pb a k` to `.pb (shAddr μ a) k` (needed because a
  `push`/`movst` of a stack pointer stores pointer bytes, and in the windows run that stored
  pointer is itself shifted);
* `shSt μ s` --- `gpr := s.gpr.map (shVal μ)`, `mem := s.mem.map (fun (a, c) => (shAddr μ a,
  shCell μ c))`, every other field unchanged; `shVal μ` shifts `.ptr ⟨rStack, o⟩` and fixes
  `.num`/other pointers.

`shSt μ` is a global bijection (each component is).  **Correction (R5, 2026-11-13):** an earlier
draft of this note claimed the per-instruction lemma is *unconditional* over `frameSafe i`.  That
is false: on 64-bit `alu add`/`sub` the model records the operand *offsets* in `flags`, and on
64-bit `cmp`/`test` it records the operands themselves, so if an operand were a stack pointer the
shifted run would record the shifted value and the two flag sets would not be `shSt`-related.
The corrected lemma carries the explicit hypothesis

`hns : ∀ j, j ≠ 4 → NoStackVal (s.getG j)`  (`NoStackVal v` = `v` is not a `rStack` pointer)

in addition to `frameSafe i`: the only stack pointer in the register file is `rsp` itself
(register 4), which `frameSafe` keeps out of every operand, and the wrapper entry state has no
other stack pointer (see below).  `rsp`-relative *memory* operands are unaffected --- `effAddr_sh`
shifts the address and `loadLane_sh`/`storeLane_sh` shift the payload.  With this hypothesis the
lemma is

`exec ro mem0w orc i (shSt μ s) = shSt μ (exec ro mem0l orc i s)`  for `frameSafe i` and `hns`,

with the ambient memory related by `∀ a, mem0w (shAddr μ a) = shCell μ (mem0l a)` and `ro ≠
rStack`.  It is now **proved** as `Proofs/WinSseExec.exec_sh` (all 39 constructors, kernel-checked
with only `propext`, `Classical.choice`, `Quot.sound`).  Every
instruction case reduces to the commutation of `shAddr` with `plusI`
(`shAddr μ (a.plusI k) = (shAddr μ a).plusI k`) plus `lookup`/`readCell` equivariance; `effAddr`
needs only that the *index* register holds a `.ptr ⟨rNum, _⟩` (`mSafe` already forbids `rsp` as
the index, and the index is a number, not a stack pointer).  `lea`/`mov` from `rsp` are fine
because `shSt` shifts the produced pointer consistently --- this is the point of shifting *all*
stack pointers in the register file rather than only `rsp`.

**The entry condition.**  The shipped windows stream differs from the linux one only in `rsp`,
so `shSt μ` can be *established* at the body entry only if no other register holds a stack
pointer: if an argument were a pointer into `rStack`, the real windows run would use the
unshifted value, whereas `shSt μ` shifts it.  Hence the functional contract carries the
side condition "no argument register holds a `rStack` pointer" (the Go wrapper passes heap and
`.rodata` pointers only).  The prologue's pushed pointer cells are *not* part of the relation:
`sse_body_footprint`/`sse_save_slots_untouched` show the body never reads the push/save area
(`[rsp+64, rsp+264)`), so the relation only has to hold on the body's own `[rsp, rsp+64)` ---
i.e. it is used as a *partial* relation, restricted to the cell set the body touches, which is
why the footprints are part of this obligation and not of the shani one.

**Status.**  `Proofs/WinSseShift.lean` holds `shAddr`/`shCell`/`shLog` and the full lemma

## 14. The shani epilogue replay and the save-slot readback (`WinShaniEpi`)

**What is proved.**  `Proofs/WinShaniEpi.lean` replays the shipped `shani_x2` epilogue from the
machine semantics and identifies what each restore actually loads.

*Geometry.*  pc 679..688 are the ten `vload false 4 (6+k) [rsp+16k]` restores
(`epi_lookup`, from `WinShani.shani_epilogue_restores`), pc 689 is `add rsp, 248`
(`epi_add_lookup`, from `shani_rsp_balanced`), pc 690 is `ret` (`epi_ret_lookup`,
`decide +kernel`).  The states are collected by `epiSt s st : Nat → State`, the `k`-th state
after writing back the `k`-th saved lane and stepping the pc.

*The replay.*  `run_epi` is the induction `run winProg k t0 = epiSt t0 st k` for `k ≤ 10`,
peeling the last step with `run_add` and then `run_succ_step` at pc `679+k`, using the
`exec_vload_ok` formula of `WinShaniFlags`.  `exec_add64_rsp` and `exec_ret_ok` are the last two
`exec` formulas (`add rsp, 248` leaves the `flags` at `((r+248).off, 0)`; `ret` succeeds exactly
when `loadVal` at `r+248` reads the return region).  `run_epilogue` composes all twelve steps
into `run winProg ro mem0 orc 12 t0 = epiFinal t0 st r`, where `epiFinal` is the halted state
with `rsp := r+256`, `flags := ((r+248).off, 0)`, `pc := 690` and the ten restored vector
registers.

*The readback.*  The epilogue restores xmm`6+k` from `[rsp+16k]`, which is the save slot of the
prologue (`shani_prologue_saves`).  To say *what* is loaded, the module builds the save log
`saveLog st r 10` (`WinShaniFront`, one `laneLog` block per 16-byte slot) and proves the
address arithmetic, the newest-first `lookup` lemmas (`lookup_hit`/`lookup_skip`/
`lookup_laneLog_lane`), the four-byte reassembly `loadLane_dat` (via
`Hashtree.Asm.bytes_reassemble`) and their `loadLanes`/`readVSrc` lifts.  The body may also
write to the stack, so `lookup_saveLog_from` skips all newer blocks and the callers carry
`Outside r 160 W` (every `rsp`-relative store of the body is at `disp ≤ 0` or `≥ 160`, from
`shani_save_slots_untouched`) to keep those writes out of the ten slots.  The payoff is
`readVSrc_save`: within the flat stack window, each epilogue `vload` reads back exactly
`(st.getV (6+k)).take 4` — the low four lanes that the prologue saved — regardless of what the
kernel did to xmm`6+k` in between, and `run_epilogue_getV` states this at the level of the
finished run.

**Why it matters.**  This closes the frame round-trip for `shani_x2` on the semantic side: the
callee-saved registers observable after the call are the low-4-lane images of their entry
values, so the register-restoration claim of the wrapper no longer depends on a model
assumption about the epilogue but on the decoded instructions.  The remaining composition step
is to feed `run_epilogue` with the body slice of section 13 (the save log being the body's
initial stack image) and to transfer the linux seed state through `shSt`, which is the next
item in the queue.

**Axiom accounting.**  All sixteen audited theorems of the module depend only on `propext`,
`Classical.choice` and `Quot.sound`, plus the allowlisted
`Hashtree.Asm.bytes_reassemble._native.bv_decide.ax_1_5` for the four-byte reassembly
(`loadLane_laneLog`, `loadLanes_laneLog`, `loadLanes_save`, `readVSrc_save`, `run_epi`,
`run_epilogue`, `run_epilogue_getV`).  `epi_lookup`, `epiSt_getV_after` and

## 15. The complete-call composition (`WinShaniCall`)

**What is proved.**  `Proofs/WinShaniCall.lean` composes the three pieces of the previous
sections into a single run of the shipped windows stream:

```
pc 0         sub rsp, 248                            run_prologue        (11 steps)
pc 11..678   the 668 shared body instructions        shani_body_transfer (n steps, loop)
pc 679..690  ten xmm restores, add rsp, 248, ret     run_epilogue        (12 steps)
```

`shani_call_run` states the prologue-and-body part: `11 + n` instructions from the ABI entry
state are the translated `n` linux body steps from the seed `seedSt st a`.  `shani_call` adds
the twelve epilogue steps and ends in `epiFinal`; `shani_call_halted`, `shani_call_rsp` (the
stack pointer comes back as `a + 8`) and `shani_call_getV` (each of xmm6-xmm15 returns with its
entry low four lanes) project the observable facts out of it.

**The save-log / view step.**  The prologue's result is `saveSt st a 10`: register `rsp` holds
`a - 248`, the flags are `some (a.off, 248)` and the memory is the prologue save log
`saveLog st (a - 248) 10 st.mem`.  The linux certificate starts from the state after
`sub rsp, 88`: `rsp = a - 88`, flags `some (a.off, 88)`, and the same memory (the linux program
does not save any vector registers).  The definition

```
seedSt st a = { gpr  := map (fun j => if j = 4 then .ptr (a - 88) else st.getG (F j)),
                flags := some (a.off, 88), pc := 1,
                mem  := saveLog st (a - 248) 10 st.mem }
```

captures both the register *renaming* (`register j holds windows register F j`) and the
`rsp` shift by 88.  `shani_seed_eq` proves

```
{ saveSt st a 10 with flags := some (a.off, 88) }
  = shiftPc 10 (renSt F G (spSt (-160) (seedSt st a))),
```

which is what the transfer engine applies.  The register-file equality is `List.ext_getElem`
elementwise: the `j = 4` case goes `G 4 = 4`, `spSt_getG_self` and `spVal`, the other cases
`G i ≠ 4` (from `F (G i) = i`), `spSt_getG_ne` and the seed's definition.  `rsp` is the one
register where the seed *overrides* `st.getG (F 4) = st.getG 4` (the entry `rsp`): the linux
frame is 88 bytes, the windows frame 248, and the entry value `a` is not the body value.

**The flags bridge.**  The state `seedSt` has the linux flags, `saveSt` has the windows ones,
and the transfer compares states including their flags.  `WinShaniFlags.run_flags` supplies the
equality of any run of length at least four from the two entries (the first four body
instructions are straight-line and the `cmp r8, 2` at pc 14 overwrites the flags before the
first branch).  It costs two side conditions, the value read by the pc-11 `vload` and the value
of `r8` at the `cmp`; the module takes them as the entry values `v` and `x`.

**What is still a hypothesis.**  The body-exit facts are explicit hypotheses rather than
conclusions:

* `hcond` -- the linux run stays in the body slice (`1 <= pc < 669`) or has halted;
* `hpc`, `hnh`, `hrsp` -- at step `n` the linux body reaches pc `669` unhalted with `rsp`
  unchanged (the linux `add rsp, 88` is at pc 669, outside the slice);
* `hW`, `hmem` -- the stack image is `W ++ saveLog st (a - 248) 10 tail` with every cell of `W`
  outside the 160-byte save area (`Outside (a - 248) 160 W`);
* `hret` -- the return pointer sits at `[a]` on the linux body-exit memory;
* `hvlen`, `hvr` -- the entry vector registers have at least four (resp. exactly sixteen) lanes.

These are exactly the facts a stack-footprint engine over the body slice has to supply
(`shani_stack_footprint`, `shani_save_slots_untouched` and an `exec`-level memory-prefix
induction); they are separated from the composition so that the composition does not depend on
how they are discharged.  Two hypotheses that *would* have been in that list are already
proved: `run_gpr_len` / `run_vr_len` (with their per-instruction engines `exec_gpr_len16`,
`exec_vr_len` over the same 39 instruction forms as `exec_ns`) give the body-exit register-list
lengths from the entry `st.gpr.length = 16` and `st.vr.length = 16`.

## 16. The body-exit stack footprint (`WinShaniWrite`, `WinShaniExit`)

**Why.**  `shani_call` (§15) takes the body-exit stack facts as hypotheses: `hrsp` (`rsp` is still
`a - 88`), and `hW` / `hmem` (the body's stack image is the prologue save log under a prefix `W`
whose cells all lie outside the 160-byte save area `[a - 248, a - 88)`).  This section proves
them from the shipped streams, so they are no longer assumptions of the call composition.

**What the body writes.**  `#eval` over the shipped 668-instruction linux body shows exactly ten
stores, all `vstore 4`: four with `base = some rsp` and displacements `0, 16, 32, 48` (on
windows: `160, 176, 192, 208` — the same absolute slots after the 160-byte frame shift), and six
through a base register at displacements `0..48`.  There is no `movst`, no `push`/`pop` and no
`rip`-relative store.  The save-area argument therefore only has to cover `vstore`, and any other
instruction is memory-inert.

**The write predicate.**  `wSafe sp0 i` (`WinShaniWrite`) is `True` for every form but `vstore`,
and for `vstore w m _` it asks: `m.ro = none`, `mSafe m`, and, when `m.base = some rsp`,
`sp0 + m.disp + 4w <= 0 ∨ 160 <= sp0 + m.disp`.  `sp0` is the offset of the body's `rsp` from the
save-area base `r`; the linux body runs with `rsp = r + 160` (the linux `sub rsp, 88` against the
windows frame base `a - 248`), which is why the predicate is not hard-wired to `0`.  `wSafeB sp0`
is its kernel-reducible mirror, with `wSafeB_iff`.

**One step.**  `exec_mem_nw` shows that an instruction outside `vstore/movst/push/pop` leaves
`mem` alone (`exec` has 39 cases, but the `EP` bind/ite/throw machinery of `X86RunHom` collapses
each to `rfl` after rewriting `State.branch`).  The three effective-address lemmas fix the address
a store computes: `effAddr_rsp` (an `rsp`-based operand without index/relocation stores at
exactly `r.plusI sp0 + disp`), `effAddr_reg` (a register base keeps the base register's region)
and `effAddr_abs` (an absolute operand has region `rNum`).  `exec_write_log` then proves

```
hr : r.region = rStack →  s.getG rsp = .ptr (r.plusI sp0) →
(∀ j ≠ rsp, NoStackVal (s.getG j)) →  wSafe sp0 i →
∃ L, (exec ro mem0 orc i s).mem = L ++ s.mem ∧ Outside r 160 L
```

with the four cases of the store address: `rsp`-based (the displacement condition clears the save
area, `4 * (take w).length <= 4w`), a `rsp`-free base register (`NoStackVal` gives a region
different from `r.region = rStack`), absolute (`rNum ≠ rStack`), or an address error (`fail`
keeps `mem`).  The region hypothesis `r.region = rStack` is what makes the register case work —
this is exactly the fact that the entry `rsp` is a stack pointer.

**The run.**  `run_write_log` is the induction over `n`: `hstep` (each in-slice instruction is
`wSafe`), `hsp` and `hns` (the two register invariants along the run) and the slice condition,
concluding `∃ W, mem = W ++ s.mem ∧ Outside r 160 W`; the log is `M ++ L` with `outside_app`.

**The invariants.**
* `exec_rsp_ns` / `run_rsp`: an `nsSafe` instruction (§`WinNs`) never writes `rsp` (every
  general-register writer of the body has `d ≠ 4`), so a run of the slice keeps `rsp` at the seed
  value `a - 88 = (a - 248) + 160` (`seed_rsp`).
* `seed_ns`: when the ABI entry state has no stack pointer in a non-`rsp` register, neither does

**The scans and the result.**  `shani_linux_ns` and `shani_linux_ws` are

```
hro : ro ≠ rStack → (∀ j ≠ rsp, NoStackVal (st.getG j)) → a.region = rStack →
hcond → ∃ W, Outside (a - 248) 160 W ∧
             (run linuxProg ro mem0 orc n (seedSt st a)).mem
```

and `shani_call_mem` is `shani_call` with `hW`, `hmem` (at `tail = st.mem`) and `hrsp`

## 17. The windows wrapper model and the kernel composition (`WinWrapperPre`, `WinWrapperMach`, `WinWrapper`)

### The certificate seed does not line up (`WinShaniSeedAlign`)

Checkpoint (a) of the follow-up asks for the body-slice functional output at linux pc 669 for
`run linuxProg n (seedSt st a)` directly from a linux certificate.  A certificate is a closed
statement about its own symbolic start state, so the seed would have to *be* that start state.
It is not: `Proofs/WinShaniSeedAlign` proves, machine-checked, that no choice of the certificate
symbols aligns them, and identifies exactly where.

At the windows call state `entryWin` the seed (with `st = mapState env sigma entryWin`) has, in
linux numbering, `rbx = ptr (rStack, sigma 6)` (the Win64 `rbp`, a wrapper stack pointer),
`rbp = num (Win64 rdi, caller data)`, and `r8 = ptr (rStack, sigma 5)` (the Win64 `rbx`, the
wrapper frame base).  `X86Sym.entryS` (`ShaniAll.shani_correct`) has `rbx` a plain number;
`X86SymW.entryW` (`ShaniW.correctW`, the closest certificate: arbitrary entry stack pointer)
has `rbp` a stack pointer and `r8` a plain number.  `mapVal` maps `num` to `num` and `ptr` to
`ptr`, so `seedSt (...) != mapState e sigma entryS` (`seed_ne_entryS`) and
`!= mapState e sigma entryW` (`seed_ne_entryW`) for every `e`, `sigma`.

The certificates are therefore not directly applicable to the seed.  What is missing is a
register-read-set (dataflow) argument: the body reads only some of the registers whose
constructors differ (an instruction scan gives zero *source* uses of linux `r8`; `r5`, `r12`,
`r15` need the same treatment), plus a run-invariance lemma for registers the body never reads
before overwriting.  No such engine exists in the tree, so checkpoint (a) as stated is not
available; this is the exact obstruction, not a failed proof attempt.  The alternatives are that
engine or a windows-specific functional certificate (the windows stream is the renamed linux
stream, so an instruction-level replay is possible but long).

Axioms of the module: `propext`, `Quot.sound` only (the `decide +kernel` scans add nothing).

### The model (`Kernels/X86Win/WrapperWindows.lean`)

The Go wrapper text is now modelled by hand (it is not in the COFF `.syso`, so the model gate
cannot generate it).  `pre F` is the assembler prologue plus the wrapper's straight-line head as
nine instructions (go1.26 expands `TEXT ·HashtreeHash(SB), 0, $F-24` into
`PUSHQ BP ; MOVQ SP, BP ; SUBQ $F, SP`):

| pc | text | note |
|---|---|---|
| 0 | `push rbp` | saves the caller's `rbp` at `SPe - 8` |
| 1 | `mov rbp, rsp` | |
| 2 | `sub rsp, F` | declared frame `F` (`shippedFrame = 0x400`, `fixedFrame = 0x800`) |
| 3 | `mov rcx, [rsp+F+16]` | `output+0(FP)` = `[SPe+8]` |
| 4 | `mov rdx, [rsp+F+24]` | `input+8(FP)` = `[SPe+16]` |
| 5 | `mov r12, r8` | saves the incoming Go `R8` in the callee-saved `r12` |
| 6 | `mov r8, [rsp+F+32]` | `count+16(FP)` = `[SPe+24]` |
| 7 | `mov rbx, rsp` | frame base for the epilogue |
| 8 | `add rsp, 0x800` | the text's fixed 2048, independent of the declared `F` |

Then `alignI` is `ANDQ $-32, SP` (`$~31`), `post F` is `mov rsp, rbx ; mov r8, r12 ; add rsp, F ;
pop rbp ; ret`, and `Kern`/`pick` model the three `CMPB`/`JE`.

### The composition

`RegsOkW σ s` fixes the Win64 callee-saved registers at the wrapper's call state (`rbx`, `rbp`,
`r12` = the incoming `r8`, `r13`/`r15`, `r14` = g) and `rsp = σ9 + 8`.  It deliberately mentions
no vector register: U6 is not assumed away.  `KSpecW kprog rodata steps D` is the windows kernel
contract at `entryWin`: from the wrapper's call state on a memory with the kernel's rodata, the
marker at `σ9` and the input bytes, every count returns after `steps c` instructions with
`halted`, no `err`, no `tail`, a footprint `Foot (σ9) D` (output bytes and stack bytes
`[σ9-D, σ9)`), the SHA-256 outputs (`OutOk`) and `RegsOkW`.

`wrapper_kernelW_core` is the frame-generic composition: given the per-frame prefix shape
(`hP`), alignment (`hA`), `KCW` shape/split/marker/`rbp` facts of the frame, and two separation
hypotheses

* `hsepM` — the marker block is entirely below `[σ9-8, σ9+8)`:
  `σ10+8 ≤ σ9-8 ∨ σ9+8 ≤ σ10`;
* `hsepK` — the kernel's writes avoid it: `σ10 ≤ σ9-8 ∨ σ9+8 ≤ σ10 - D`;

it proves `wrapRunW` (prefix, alignment, `CALL`/`callK`, kernel, epilogue) ends halted with no
`err`/`tail`, `rsp = σ9+8`, `rbp = ⟨rStack, σ6⟩`, `r8 = ⟨rNum, σ13⟩`, every write an output byte
or a byte of the kernel's frame `[σ10-D, σ10)`, the marker `[σ10, σ10+8)` or the saved `rbp`
`[σ9-8, σ9)`, `OutOk`, and — when `σ9 ≤ σ10` — the witness that the call wrote above `σ9`
(the marker at `σ10`).

The two frame theorems read the union of those ranges off:

* `wrapper_kernelW_fixed` (`D ≤ 2009`, `hA` fixed): the three ranges plus the caller's saved
  `rbp` tile `[σ9-2056, σ9)`, so the conclusion is exactly the linux-shaped, Go-facing contract
  `Foot (σ9) 2056 (σ1) (32*c) fin.mem ∧ OutOk ...` plus the register/rsp facts.
* `wrapper_kernelW_shipped` (`hD9 : σ9+8 ≤ σ10 - D`, `hA` shipped): the ranges tile
  `[σ9-8, σ10+8)`, i.e. the saved `rbp` slot and the caller's frame above `SPe`; the theorem
  also proves `∃ p ∈ fin.mem, p.1.region = rStack ∧ σ9 ≤ p.1.off` (the marker) and
  `¬ Foot (σ9) 2056 ...`: the linux-style footprint claim is **false** for the shipped text.
  Since `σ10 ≥ σ9+977`, `hD9` holds for any kernel with `D ≤ 969`: shani_x2 (248), sse_x1 and
  avx_x1 (264), avx_x4 (568), avx512_x16 (0; it tail-calls rather than framing).  avx2_x8
  (1264) does **not** fit, so the shipped wrapper cannot be proved for it.  The witness below
  proves the failure concretely: the `avx2_x8` loop's input-derived 32-byte store overwrites the
  wrapper's saved-`rbp` and return-address slots `[σ9-8, σ9+8)`.  This is the shipped-frame
  defect (section 7); the fix branch's `$2048` removes it.

`wrapper_correctW` dispatches with `FitsW` hypotheses for the four kernels (exactly as the
linux `wrapper_correct` does with `Fits`): `pick` selects the kernel, and the fixed-frame
contract above is concluded.  `FitsW k` is `∃ steps D, D ≤ 2009 ∧ KSpecW (kprogOfW k)
(krodataOfW k) steps D`; no kernel instance is proved yet (next paragraph).

## 18. The run-invariance engine (`Asm/RunAgree`) and the shani certificates

Section 17 left checkpoint (a) at an exact obstruction: the windows seed and the linux
certificate start state differ in the constructor of registers the body never reads before
writing, so what was missing was a run-invariance lemma over the body's read set.  This section
is that engine, kernel-independent, and its instantiation for the two shani programs.

### The relation

`Agree R s1 s2` (`Hashtree.Asm.RunAgree`): the two states are equal on `vr`, `flags`, `mem`,
`pc`, `halted`, `tail`, `err`, have general-register lists of the same length (a `List.set`
past the end is a no-op, so the lengths must be in step for writes to agree), and agree on the
general registers in `R` (`∀ r ∈ R, s1.getG r = s2.getG r`).  The recorded branch assumptions
are deliberately excluded (they are written, never read).  Full memory agreement is the
relation the shani instance has; the push-saving bodies need a weaker one (below).

### The step lemma

`exec_agree`: from `Agree R s1 s2` and `srcs i ⊆ R`,

* `Agree R (exec i s1) (exec i s2)`, and
* either the pc is unchanged (the step failed, or a jump to itself), or the new pc is a static
  successor (`succs pc i`: `pc+1`; `jcc` also `t`; `jmp` only `t`; `jccTail` `pc+1`;
  `jmpTail`/`ret` none) **and** `Agree (dsts i ++ R)` holds.

The proof is one case per `Instr` constructor (46), each mechanical: the reads of `s2`
(`getV`, `getG` on `R`, `effAddr`, `loadLane(s)`, `loadVal`, `readVSrc`, `gData32`, `gCtl`) are
rewritten to the reads of `s1`, after which the two `Except` computations are the same
computation applied to two writer bases; a lifting `AgreeE` through `bind`/`pure`/`throw` and a
writer tactic (`next`, `setVec`, `setG` adds its register, `setData32`, `storeLane(s)`,
`storeVal`, `clearFlags`, `setFlags`, `halt`, `branch`) close each branch.  No constructor
needed a special semantic case; two needed hand ordering (`pop` writes `r` then `rsp`;
`jccTail` halts with the entry pc).

### The scan had to be completed

`BodyReads.srcs/dsts` (commit c3e36d2) had no entries for `test`, `shl`, `bswap`, `push`,
`pop`, `ret` and did not count the index register of a memory operand; `exec_agree` is false
against that scan (`test r8,r8` is windows shani pc 446, inside the body).  Commit 25399bc
completes it (`memRegs m = base ++ index`; `push` reads `rsp` and its register and writes `rsp`;
`pop` reads `rsp`, writes `r` and `rsp`; `ret` reads and writes `rsp`; `shl`/`bswap`/`test`
read their operands).  The shani tables `[2,6,4,7]`/`[8,2,4,1]` re-decide unchanged.

### The run: a per-pc certificate, not the linear scan

The linear `rbw` of a stream is **not** a valid invariant for the pc-driven `run`: a forward
jump over a write reads a register the linear scan reports as written first, and the loop
back-edge (windows shani: pc 445 `jmp 14`, with pc 15 `jl 446` and 447 `je 679`) needs the
loop-head reads at the loop end.  The sound form is the classic live-variable certificate
`Cert prog L`: for every pc `p` with instruction `i`, `srcs i ⊆ L p` and for every static
successor `q`, `L q \ dsts i ⊆ L p`.  `run_agree`: `Cert prog L → Agree (L s1.pc) s1 s2 →
Agree (L (run n s1).pc) (run n s1) (run n s2)` for every fuel `n`, same `prog`/`ro`/`mem0`/`orc`
(induction on `n`; a failed step keeps its pc, a successful one lands on a successor).

`certB prog L` decides the certificate (`Cert_of_certB`), `live prog` computes one: backward
sweeps from the last pc (forward successors read the current sweep, back-edges the previous
one) to a literal fixpoint (fuel 16).  The linear `rbw` reappears as the entry set: for all six
windows kernels and the linux shani program the certificate checks, the fixpoint is reached,
and the entry live set equals the rbw table.

| program | size | entry pc | live entry set = rbw |
|---|---|---|---|
| linux shani_x2 | 671 | 1 (after `sub rsp,88`) | `[2, 6, 4, 7]` |
| windows shani_x2 | 702 | 11 (after the prologue) | `[8, 2, 4, 1]` |
| windows sse_x1 | 4243 | 0 | `[4, 3, 8, 6, 7, 5, 12, 13, 14, 15, 1, 2]` |
| windows avx_x1 | 4116 | 0 | same as sse_x1 |
| windows avx_x4 | 4163 | 0 | `[8, 4, 9, 2, 1]` |
| windows avx2_x8 | 6107 | 0 | `[8, 4, 5, 6, 12, 13, 14, 15, 2, 1]` |
| windows avx512_x16 | 3292 | 0 | `[8, 4, 2, 1]` |

So one engine covers all six bodies at the instruction level.  The sets of sse_x1/avx_x1/avx2_x8
contain the Win64 callee-saved registers because the bodies `push` them (`movst` on avx2_x8):
their entry values flow into the kernel's own frame cells and back out through `pop`.  With full
memory agreement in `Agree` they are reads; the bridge for those bodies needs memory agreement
on all cells except the kernel frame plus a frame-slot liveness certificate (every read of a
frame cell preceded on all paths by a write of it), which is the planned extension; shani,
avx_x4 and avx512_x16 do not push and have the small sets above.

### The shani instances (`WinShaniSeedAlign` §Live)

`linuxLive`/`winLive := live prog`; `shani_linux_certB`/`shani_windows_certB` (`certB = true`,
`decide +kernel`), `shani_linux_cert`/`shani_windows_cert` (the `Cert` the bridge hands to

outside `[2, 6, 4, 7]`, and the four inside agree up to the σ relabelling of section 17.

Axioms: `exec_agree`, `run_agree`: `propext`, `Classical.choice`, `Quot.sound`;
`Cert_of_certB`, `shani_*_cert`, `shani_*_live_entry`: `propext`, `Quot.sound`; the kernel

## 19. Checkpoint (a): the positive shani bridge and `FitsW .shani` (`WinShaniBridge`)
