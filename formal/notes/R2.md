### Architectural findings for the remaining multi-lane work

1. **The multi-lane kernels never return; they tail-call the next kernel down.** x4's only
   `ret` is the count-0 path at pc 3. For c ≥ 1 it ends at
   `jmpTail hashtree_sha256_avx_x1` (pc 4143) after `add rsp,408`, with the *first* kernel's
   stack frame already popped but its `.rodata` still in region 4. x8 tails x4, x16 tails x8.
   `KSpec` requires `fin.tail = none` and `callK` runs exactly one program, so a `KSpec` for
   x4/x8/x16 cannot be proved by running one `kprog`; the wrapper model has to gain a
   tail-following chain (`runChain` in `X86Run.lean` is the validation-harness analogue; the
   proof side needs the same with per-program `ro` and a memory holding every chain member's
   rodata at its own region).
2. **Each object's `.rodata` overlaps the others and is not the linked layout.** Object-local
   read offsets: x4 = {0, 1024, 2048, 2176}, x8 = {0, 2048, 4096, 4352},
   x16 = {0, 4096, 4160, 8256, 8768, 8832, 8896, 8960}, x1 = {0, 256, 288, 544, 560, 576},
   shani = {0, 256, 272, 288, 304}. They collide at 0 (x4's is a 4-way broadcast K table, x1's
   is the scalar K table), so one region-4 `mem0c` cannot serve two chain members. A chain
   must run each kernel with its own ro region (`run`'s `ro` argument is exactly that region
   number); `WfMemW` is currently hardcoded to region 4 and has to be generalized or
   instantiated per member.
3. **The x4 body uses the 408-byte stack frame** (112 rsp-based memory operands), so the
   `entryW` stack layout (`sAt`/`pushL`/return marker at `σ 9`) really is different from the
   `entryS 24` layout used by the fixed-count `AvxX4P`/`Avx2X8P`/`Avx512X16P` certificates.
   Those certificates cannot be replayed at `entryW` through `Mem0Rel`: `mem0s 4 rodata 24`
   constrains stack address 24 to the return cell, which at `entryW` lives at `σ 9`. The
   all-count body segments must be regenerated in W mode (`mem0sW`, `pushL`, `entryW`), as
   `AvxX1LW` was for avx_x1.
4. **Dead-register/flag state at the tail.** The x4 exit state differs from `entryW` in rax,
   rcx and flags (all dead for x1) and in rdx/rsi/rdi (advanced output/input pointers, count =
   remainder). Composing x1 at that state needs either an x1 contract parameterized by those
   dead values or a small dead-register invariance lemma; `AvxX1W.correctW` is stated exactly
   at `entryW`, so it is not directly instantiable.

The next increment is a W-mode multi-lane segment generator (`X86LoopVW`) producing, for each
of x4/x8/x16: the `entryW` prologue to the loop head, one `W`-block iteration head→head under
`(in +64W, out +32W, count −W)`, and the exit head→tail segment; then the chain composition
with `AvxX1W` (x4), the x4 chain (x8) and the x8 chain (x16), and the `Fits` facts.
