### Architectural findings for the remaining multi-lane work

1. **The multi-lane kernels never return for `c ≥ width`; they tail-call the next kernel down.**
   x4's only `ret` is the count-0 path at pc 3. For `c ≥ 1` it ends at `jmpTail
   hashtree_sha256_avx_x1` (pc 4143); x8 tails x4, x16 tails x8.  The real C API
   (`src/hashtree.c`) dispatches on CPU features only and `src/test.c` calls e.g. x4 with
   counts 8 and 6, so the tail calls are part of the contract for arbitrary counts.
   `KSpec` requires `fin.tail = none` and runs one program, so no `KSpec` for x4/x8/x16 can
   hold for arbitrary `c`: the wrapper model needs a tail-following chain with a per-member
   `ro` region and a memory holding every member's rodata.
2. **Each object's `.rodata` overlaps the others and is not the linked layout.** Object-local
   read offsets: x4 = {0, 1024, 2048, 2176}, x8 = {0, 2048, 4096, 4352},
   x16 = {0, 4096, 4160, 8256, 8768, 8832, 8896, 8960}, x1 = {0, 256, 288, 544, 560, 576},
   shani = {0, 256, 272, 288, 304}. They collide at 0 (x4's is a 4-way broadcast K table, x1's
   the scalar K table), so one region-4 memory cannot serve two chain members, and x1 reads
   rodata even at count 0.  `run` already takes `ro`; the proof side must generalize
   `mem0sW`/`WfMemW`/`mem0RelW_of_wf` (currently hardcoded to region 4) and re-elaborate the
   chain members' slice checks at their own regions (the cut states in the generated proofs
   also contain the region number literally, e.g. `K1.gpr[1] = .ptr ⟨4,0⟩`).
3. **The x4 body uses the 408-byte stack frame.** The `entryS 24` layout of the fixed-count
   pilots and the `entryW` layout (return marker at `σ 9`) differ by the shift `σ 9 − 24`;
   all stack addresses shift uniformly, but the pilot's proofs are stated at `entryS 24`
   with `mem0s 4 rodata 24`, while a `KSpec` starts from `entryW` with `mem0sW 4 rodata []`
   (ret at `sAt 0`).  A W-mode version of the entry/loop/exit segments is needed, or a
   stack-shift homomorphism from the entryS proofs.
4. **Dead-register/flag state at the tail.** At the x4 tail state rdx/rsi/rdi are advanced
   pointers/count; rax/rcx/r8–r11 and flags differ from `entryW` and are dead for x1 (x1's
   first flag read is the `cmp` at pc 13, after the prologue).  `AvxX1All.correctW` is stated
   exactly at `entryS 24`, and `AvxX1W.correctW` exactly at `entryW`; composing at the tail
   needs either a contract parameterized by those dead values or a dead-register invariance
   lemma (the existing `gprRel`/`mapState_inst` only replaces number lanes by location
   variables, not arbitrary pointer leftovers).
5. **x8's stack shift is not a simple tail jump shape.** x8 does `push rbp; mov rbp,rsp;
   and rsp,-32; sub rsp,928`, saves r12–r15, and on exit restores them, `mov rsp,rbp;
   pop rbp; jmpTail x4`.  A chain model has to account for the 8-byte push and the 32-byte
   alignment between the x16 and x8 frames; x16 itself has no stack frame.  The wrapper's own
   `and rsp,-32` is already modelled concretely (`align_hom`/`alignStep`).

The next increment is the W-mode multi-lane segment generator (`X86LoopVW`) producing, for each
of x4/x8/x16, the `entryW` prologue to the loop head, one `W`-block iteration head→head under
`(in + 64W, out + 32W, count − W)`, and the exit head→tail segment; then the chain composition
with the scalar kernel (x4→x1, x8→x4→x1, x16→x8→…) at distinct rodata regions, and the
`Fits .avx2`/`Fits .avx512` facts.  The x4 loop-head segmentation above is the body half of
that generator's output and is reusable as soon as the entryW↔entryS bridge exists.
