## Contract (what the kernels are claimed to do)

The three RV64 kernels (`hashtree_sha256_riscv_x1`, `..._zbb_x1`, `..._crypto`) implement

    void hashtree_hash(const void *out, const void *in, size_t count)

in the LP64D calling convention: `a0 = out`, `a1 = in`, `a2 = count`, `ra` = return address,
`sp` = stack.  `count` is the number of 64-byte input blocks (unlike the x86 SHA-NI kernel, where
the unit is a 64-byte block too, but two are processed per iteration).  For every `count` the
kernel writes `32*count` output bytes; output byte `32*n + j` is byte `j` of
`SHA-256(pad(block n))`, where `pad` is the fixed padding block (the kernel hashes every 64-byte
block independently, starting from the same `.LDIGEST` constants, with the precomputed padding
words at `.LPADDING`; this is exactly `Hashtree.Spec.blk inp n`).

* `count = 0`: no output, no memory writes; returns.
* the kernel reads only the input bytes, its rodata (`.LK256`/`.LDIGEST`/`.LPADDING`), and stack
  bytes it wrote itself; it writes only the output and its own 80-byte frame.
* `s9`/`s10` are saved in the prologue and restored in the epilogue (so the kernel is
  callee-save clean for those; the other s-registers are untouched).  Register preservation is
  proved separately from the memory/output contract (see "wrapper" below).
* the model has no alignment assumptions: the input and output pointers may be any int64.
  The Go wrapper's `sp = 8 (mod 16)` invariant (B7) is a separate statement about the wrapper,
  not about these kernels (which only assume `sp` points to the 80-byte frame they allocate).

Steps (model instruction count), measured from the generated programs (2026-11-12):

| kernel | len | loop head `H` | head | iteration | exit | `steps(c)` |
|---|---|---|---|---|---|---|
| `x1` | 6312 | 7 | 7 | 6300 | 6 | `13 + 6300*c` |
| `zbb_x1` | 4152 | 7 | 7 | 4140 | 6 | `13 + 4140*c` |
| `crypto` | 2742 | 6 | 6 | 2732 | 5 | `11 + 2732*c` |

Segment meanings: **head** = prologue `pc0..H` (ends at the loop head); **iteration** =
`H` (branch to the body taken) plus the body `H+2..L` ending with `jal 0,H` back to `H`, i.e.
`L - H` steps returning to `H` (`x1`: `7 -> 9..6307 -> 7`, `6307 - 7 = 6300`); **exit** = `H`
(branch not taken when `a0 = a2`) plus `H+1` (`jal 0,epilogue`) and the epilogue.
Bodies end with `addi a0,a0,32; jal 0,H`; all three kernels have identical data bodies
except the byte-swap of the two output words holding the length/counter (`slliw`/`lui`/`and`/`or`
for x1, `rev8`/`srai` for zbb_x1 and crypto).

Prologue/epilogue save slots: `x1` and `zbb_x1` save `s9,s10` (`sd 26,64(sp); sd 25,72(sp)`) and
restore them in the exit; `crypto` saves only `s9` (`sd 26,64(sp)`).  All three allocate an 80-byte
frame (`addi sp,sp,-80`), so the saves occupy `[-16,0)` and the body uses `[-80,-17)` only.

## Existing count-2 proofs (baseline)

`RvProof.lean` generates `Gen.Rv{X1,ZbbX1,Crypto}P.{Base,D0..,P0..,Final}`: symbolic slices over
`Riscv.run` from `entryS 0` (concrete `sp = 0`), cuts after every instruction that first produces
an `A n r t` (and at most 70 steps apart), needed location variables found backwards from the 64
output bytes of the two-block run.  It covers exactly `count = 2` because the run is a single
straight-line symbolic run of 12613 steps; there is no induction over the loop.

## Every-count proof (in progress)

Following `X86Loop.lean` + `Proofs/ShaniAll.lean`:

* `Hashtree/Asm/RiscvFrame.lean`: `fr`/`view` framing for `Riscv.exec`/`Riscv.run`
  (`exec_fr`, `run_fr`), reusing the machine-independent log lemmas from `X86Frame.lean`.
  Checked (bare `lean`, private oleans).
* `Hashtree/Asm/RiscvReach.lean` (new, builds): the reopening theorem for a loop head when the
  body leaves 32-bit data values in registers.  The x86 route (`It.KF_shape`:
  `{KF with mem := [], assume := []} = KH.substL tauE`, decided by `decide`) *fails* here: the
  body leaves constants in dead registers (x1 run: `gpr14 lo = 0x00ff0000`/`hi = 0`,
  `gpr16 lo = 0x0000ff00`, `gpr25 hi = 0`) where `KH` has location variables, so the equality is
  false.  Instead `GprLive R K0 τ` requires only:
  * pointer registers of `K0` (here `a0,a1,a2,a3,sp,ra`) to reappear in `R` under `substL τ`;
  * register `i` of `K0` holding a number to be exactly the location variables
    `.var (.n 2i)`/`.var (.n 2i+1)` of its own position;
  * every other register of `R` to be a number.
  `gprLiveRel` is the decidable checker (a `Bool`), `gprLiveRel_sound` turns it into `GprLive`,
  and `mapState_reached_vars` proves
  `mapState (envAbs env R) σ' (abstract R) = fr (R.mem.map ...) (mapState (envAbs env R) (sigmaOf τ σ') K0)`
  given `CutOk R` and the cut's pc/halted/err/tail/vr/flags facts.  The key point is that
  `envAbs env R (.n 2i)` evaluates `KH`'s data variable to exactly whatever the iteration computed
  (`gpr_map_live`), so no shape equality of data lanes is needed.  Also `sigmaOf_nil`.
* `RvLoop.lean` (planned): generator for the `head`, `it`, `t0` segments of each kernel, reusing
  the RvProof slice machinery (helpers must move to a `RvLib.lean` imported by both exes; separate
  `main`s cannot coexist in one module).  `head`: `H` steps from `entryS 0`, cut `Rhead`,
  `KP := abstract Rhead`, `KH := {KP with mem := [], assume := []}`, `slicePro`.  `it`: run from
  `KH` (memory dropped, oracle at `H`) for the kernel's iteration length, cut `KF`; the reopening
  data are the decidable `gprLiveRel KF KH tauE`, `KH` ok facts, `CutOk KF/Rhead`.  `tauE =
  [a1+64, a0+32, a2-1]` (in `Lin` symbols 0,1,2).  `t0`: the exit, which reads the prologue save
  slots; its symbolic initial memory models exactly the 8-byte slots `[-16,0)` as memory keys
  (`.dat (.var (.m rStack ⟨o,[]⟩)) ((o+16)%4)`; x1/zbb_x1 two slots `[-16,-8),[-8,0)`, crypto one
  slot `[-16,-8)`) and leaves the rest as `mem0s`, so the loads are symbolic and `Mem0Rel` holds
  against the accumulated frame log at those addresses (never overwritten: the body writes only
  `[-80,-17)`, opcode slots, and the output).
* `Hashtree/Proofs/RvAll.lean` (planned): induction on the remaining count; per iteration the
  frame log of earlier writes is moved into the initial memory (`run_fr`),
  `mapState_reached_vars` restarts at `KH`, output range/log invariants as in `ShaniAll.lean`.
  `InRange` for RV must allow the output `[ob, ob+32*count)` (offset cell `[0,1]` in `out.c`) and
  the stack `[-80,0)`; output blocks are 64 bytes, outputs 32 bytes (`outOk_new`/`blk_shift` with
  a 32-byte output stride).

Assumptions carried by the theorem: `WfMemR` (rodata/GOT/input shape), `EnvMem`, `HMem` (input
bytes), `σ 2 = count`, and `count < 2^58` (the kernel's `slli a2,a2,5` records the noWrap
conditions `-2^63 ≤ 32*count < 2^63` at the loop entry).

## Validation of the reopening design (runtime, `RvShapeTmp2.lean`)

For all three kernels, with the kernel's own head length, loop head `H` and iteration length, and
`tauE = [a1+64, a0+32, a2-1]`, the symbolic run of the generated program over
`mem0s 10 11 rodata gotPtrs` gives: `err = none`, `gprLiveRel KF KH tauE = true`,
`gprLiveRel Rhead KH [] = true`, all `KH` registers are pointer or own-variable (KHok),
`vr`/`flags` empty, `CutOk` true for `KF` and `Rhead`, and `pc`/`halted`/`err`/`tail` equal to
`KH`.  x1: 6300 steps / 320-frame cells; zbb_x1: 4140 steps; crypto: 2732 steps.  (The x86-style
`KF_shape` equality is false for all three; the false lanes observed for x1 are listed above.)
